## 結論

**`photos` を `indexed: true` に切り替えた。`media` は `indexed: false` のまま残した。**

|                                    |       中央値 | 備考                                                 |
| ---------------------------------- | -----------: | ---------------------------------------------------- |
| `indexed: false`(`R2.list()` 経路) | **17.69 ms** | 5 回、`GET /api/buckets/photos/objects?prefix=perf/` |
| `indexed: true`(索引経路)          |  **7.35 ms** | 同じ URL・同じデータ・同じ手順                       |
|                                    |  **2.41 倍** |                                                      |

**受け入れ基準は 7 件すべて満たした。**ただし基準 2(検索)と基準 6(バックフィル)には、
数字の意味を狭める注記がある。下の「受け入れ基準の判定」に書いた。

**この計測が言っていないこと**は末尾にまとめてある。**ローカル miniflare 上の数字であり、
本番の Durable Object でも同じ比になるとは限らない。**

## before / after

### 1 ページ目(`prefix=perf/`、10,000 件のフォルダ)

5 回だとばらつきが大きい(基準線の最大値 55.29 ms は 1 本だけ飛んでいる)ので、

| `indexed: true`  |       **7.63 ms** |  6.17 ms | 21.32 ms |
|                  |       **2.04 倍** |          |          |

**どちらの取り方でも索引経路のほうが速く、2 倍前後である。**5 回の中央値(2.41 倍)を
そのまま「2.4 倍速い」と読むのは楽観的で、**2 倍前後と読むのが妥当**である。

### 2 ページ目(cursor 経由)

|                  | 1 回計測 |
| ---------------- | -------: |
| `indexed: false` | 15.68 ms |
| `indexed: true`  |  9.08 ms |

1 ページ目と同じ傾向。**R2 の cursor 走査は「深いページほど遅い」形ではない**ので、
ページを進めても差が広がるわけではない。

### 何が速くなっているのか

**1000 件を返す仕事そのものは両方とも必要**なので、差は「1000 件をどこから読むか」だけである。
R2 経路は miniflare の R2 実装(これも SQLite)にメタデータを問い合わせ、索引経路は
DO の SQLite で `WHERE parent_prefix = ? ORDER BY key LIMIT 1001` を撃つ。
**索引経路の勝ち幅がこの程度に留まるのは、ローカルでは R2 も同じマシンの SQLite だからである。**
本番では R2 がネットワーク越しになるので差は広がる方向に動くと考えられるが、**測っていない。**

## バックフィル

**空の索引に対して R2 の 10,000 件を取り込む**測定。索引 DO の状態
(`apps/web/.wrangler/state/v3/do`)を削除してから `POST /api/buckets/photos/index/backfill` を叩き、
`GET .../index/status` を 50ms 間隔でポーリングした。

|                            | 実測                                                                                        |
| -------------------------- | ------------------------------------------------------------------------------------------- |
| 所要時間                   | **4.61 秒 〜 5.56 秒**(下は最後に `running` を観測した時刻、上は `complete` を観測した時刻) |
| ページ数(`backfill_pages`) | **10**(= 10,000 ÷ 1,000)。DO の SQLite を直接読んで確認                                     |
| 取り込み件数               | 10,000(`status` の `indexed`)                                                               |
| 索引 DB のサイズ           | 3,604,480 bytes(1 オブジェクトあたり約 360 bytes。FTS5 込み)                                |
| スループット               | **約 1,800〜2,200 オブジェクト/秒**                                                         |

**所要時間が範囲でしか出せないのは、バックフィル中は `status` の呼び出し自体がブロックされるからである。**
Durable Object は単一スレッドなので、`alarm()` が 1 ページ(1,000 件の upsert)を回している間、
同じ DO への RPC は待たされる。実測したポーリングの応答時間は 1.29 秒 / 3.21 秒 / 0.89 秒だった。

### Task 10 のレビュー指摘への回答

> `upsert` が 1 オブジェクト = 1 トランザクション。1 ページ = 1000 トランザクション。

**実測値は「10,000 件 = 10,000 トランザクションで約 5 秒」である。**1 オブジェクトあたり
約 0.5 ms。10,000 件のバケットならこのままで実用範囲だが、**次の 2 つが実際に起きている。**

1. **バックフィル中、その DO への読み取りが最大 3.2 秒ブロックされる。**
   `indexed: true` のバケットで運用中にバックフィルを叩くと、その間の一覧が固まる。
   **運用手順としては「`indexed: false` の状態でバックフィル → complete を確認 → `true` にして再デプロイ」
   の順を守れば踏まない**(今回もその順で切り替えた)
2. **ローカルでは R2 経路の一覧も巻き添えで遅くなる。**バックフィル中に `media`(R2 経路)へ
   一覧を投げると 1.94 秒 / 2.94 秒 かかった(平常時 約 16 ms)。
   **これは miniflare が R2 も DO も同じプロセス・同じディスクに置いているためで、本番では起きない**

100,000 件規模になると 50 秒程度になる計算であり、**そこで初めてバッチ upsert
(1 トランザクションに N 件)を検討する価値が出る。**今の規模では最適化しない。

### 2 回目(冪等な再実行)

すでに 10,000 行が入っている上に同じバックフィルを流したところ、**`complete` の観測が 7.91 秒**だった
(ポーリング間隔が粗く上限が緩いので、1 回目と厳密には比較できない)。
**`INSERT ... ON CONFLICT DO UPDATE` は行が既にあっても同じだけ書くので、再実行は安くならない。**

### マッチの意味 — 「部分一致」ではなく「トークンの前方一致」である

対象キー `perf/00009-meeting-notes-final-v2.bin` に対する実測。

| クエリ          | ヒット | 何が起きているか                    |
| --------------- | ------ | ----------------------------------- |
| `meeting`       | ✅     | `-` / `.` でトークン分割された 1 語 |
| `notes`         | ✅     | 同上(**名前の途中の語でも引ける**)  |
| `final`         | ✅     | 同上                                |
| `v2`            | ✅     | 同上                                |
| `00009`         | ✅     | 数字も 1 トークン(1 件だけヒット)   |
| `meeting-notes` | ✅     | 複数トークンのフレーズ検索          |
| `eeting`        | ❌     | **トークンの途中からは引けない**    |
| `otes`          | ❌     | 同上                                |

**「ファイル名の部分一致」と言えるのはトークン単位までである。**`LIKE '%eeting%'` のような
任意位置の部分文字列検索は FTS5 では引けない。ASCII のファイル名は区切り文字が多いので
実用上ほとんど困らないが、**日本語では困る。**次節がその実測である。

### 日本語(Ruling 17)の実測

`perf/休暇の写真.jpg` を索引に入れて計測した。

| クエリ             | `休暇の写真.jpg` にヒットするか | 実測                     |
| ------------------ | ------------------------------- | ------------------------ |
| `休暇の写真`(全体) | ✅                              | 116.8 ms(初回・コールド) |
| `休暇`(先頭)       | ✅                              | 8.1 ms                   |
| `休`(先頭 1 文字)  | ✅                              | 37.5 ms                  |
| `写真`(末尾)       | ❌                              | 6.8 ms                   |
| `暇の写`(中間)     | ❌                              | 15.4 ms                  |

(時間は 1 回計測なのでばらつく。**ここで見るべきはヒット / ミスであって時間ではない。**)

**FTS5 の既定 tokenizer(unicode61)は、連続する CJK 文字列の全体を 1 トークンにする。**
`休暇の写真` はまるごと 1 語なので、引けるのはその**前方一致だけ**である。
`tokenize = 'trigram'` に変えても解決しない — FTS5 の trigram は 3 文字未満のクエリに
マッチしないので、`写真` のような 2 文字の日本語クエリはそもそも構成できない。

**この実測値が、spec の「Phase 5(Vectorize 意味検索)の要否は FTS5 を実際に使ってから判断する」の
判断材料である。**判断材料としての読み方は次のとおり:

- **ASCII のファイル名しか扱わないなら FTS5 で足りる。**トークン単位の前方一致で実用になる
- **日本語のファイル名を「末尾」「中間」で引きたいなら FTS5 では届かない。**
  打ち手は 3 つあり、コストが違う:
  1. **形態素解析 tokenizer**(MeCab / Lindera 等)。DO の SQLite に持ち込めるかは未調査
  2. **N-gram(bigram)を自前でトークン化して `objects_fts` に入れる。**FTS5 のままで
     日本語の中間一致が引ける。索引サイズは増える
  3. **Vectorize(Phase 5)。**意味検索まで欲しくなったときの選択肢であって、
     **「中間一致が引けない」だけの理由で持ち出すには重い**

**つまり Phase 5 の要否は、この実測だけでは「まだ決まらない」。**先に 2 を試す価値がある、
というのが今回の実測から言えることである。

## Ruling 18(cursor の経路タグ)— 切り替えの前提条件

**`indexed: false → true` の切り替え deploy の瞬間、スクロール中のクライアントが握っている
R2 の opaque cursor が索引経路に渡る。**索引側はそれを `WHERE key > '<その文字列>'` として
素直に解釈するので、**エラーにならず静かに間違ったページを返す。**

実測した R2 の cursor は `bXBlcmYvMDA5OTktbWVldGluZy1ub3Rlcy1maW5hbC12Mi5iaW4=`(base64、52 文字)である。
`'perf/00000-a.jpg' > 'bXBlcmYv...'` は `'p'`(0x70)> `'b'`(0x62)なので真になる。
**つまりタグが無ければ「1 ページ目をもう一度返す」が延々続き、利用者から見れば
スクロールしても同じファイルが並び続ける。**一覧で沈黙して間違うのは最悪の失敗モードである。

対処として `ObjectIndex.list` / `search` が返す cursor に経路タグを付けた(`fbe5ca8`)。

|          | タグ  | 例                                         |
| -------- | ----- | ------------------------------------------ |
| `list`   | `k1:` | `k1:perf/00999-meeting-notes-final-v2.bin` |
| `search` | `q1:` | `q1:perf/00999-meeting-notes-final-v2.bin` |

**`list` と `search` でタグを分けた。**検索は prefix を持たないので、検索の cursor を一覧に
渡すと別フォルダのキーを起点に走査してしまい、これも静かに間違う。

区切りに `:` を使うのは R2 の cursor と衝突させないためである(実測した R2 の cursor は
base64 で `:` を含まない)。数字は形式のバージョンで、cursor の意味を変えるときに上げれば
古い cursor が自動的に foreign として弾かれる。

`NextPage.cursor` はクライアントから見て opaque な `string` なので、**タグ付けはワイヤ互換である**
(`ObjectDescriptor` / `NextPage` / `ObjectPage` の型は変わっていない)。

### 実際の HTTP の口での確認(切り替え後)

| 送ったもの                                        | 結果                                                                                                          |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `media`(R2 経路)の cursor を `photos`(索引経路)へ | **412** `{"name":"PreconditionFailedError","message":"cursor was not issued by the object index list route"}` |
| `photos` の検索が発行した cursor(`q1:`)を一覧へ   | **412**(同じボディ)                                                                                           |
| `photos` の一覧が発行した cursor(`k1:`)を一覧へ   | **200**、2 ページ目(`perf/01000-a.jpg` から)が返る                                                            |

**wire に出る名前を `PreconditionFailedError` にしたのは、`packages/core` の `ErrorName` を
増やさないためである**(このタスクは `packages/core` を変更しない前提で走っている)。
内部のクラスは `ForeignCursorError` のままなので、ログ(`describeCauseChain`)では粒度が落ちない。
**素直なのは `ErrorName` に `'ForeignCursorError'` を足して 400 で返すことなので、
`packages/core` を触れるタイミングで移すべきである。**

### 副産物 — DO の RPC 境界はクラスを落とし、`name` だけ残す

実測(vitest-pool-workers 上、`BucketMismatchError` を DO 越しに受けた):

|                                  | 越えた先                                |
| -------------------------------- | --------------------------------------- |
| `instanceof BucketMismatchError` | **false**                               |
| `constructor.name`               | `'Error'`                               |
| `.name`                          | `'BucketMismatchError'`(**保存される**) |
| `.message`                       | 保存される                              |

`packages/api/src/object-index/errors.ts` と `packages/core/src/errors/index.ts` が言う
「name は RPC / JSON を越えた先の wire 判別子」がそのまま実測で裏付けられた。
消費エッジの responder は `instanceof` ではなく `name` で判別している。

## 受け入れ基準の判定(spec §13)

### 1. 索引済みバケットで 10,000 件のフォルダの 1 ページ目が `R2.list()` 経路より速く返る ✅

**確認方法:** 同じ 10,000 件・同じ URL(`GET /api/buckets/photos/objects?prefix=perf/`)に対し、
`packages/api/src/r2/registry.ts` の `indexed` だけを `false` → `true` にして dev を再起動し、
ウォームアップ 2 回 + 計測 5 回の中央値を取った。

**17.69 ms → 7.35 ms(2.41 倍)。**同じ条件で 20 回ずつ取り直すと 15.58 ms → 7.63 ms(2.04 倍)。
**取り方によらず索引経路が速い。**

### 2. ファイル名の部分一致検索が 10,000 件から返る ✅(**「部分一致」の意味は狭い**)

**確認方法:** `GET /api/buckets/photos/search?q=meeting` を実行し、10,005 行の索引から
100 件(`SEARCH_PAGE_SIZE`)が `next: more` 付きで返ることと、中央値 7.36 ms を確認した。

**満たしているが、引けるのは「トークンの前方一致」であって任意位置の部分文字列ではない。**
`meeting` / `notes` / `final` / `v2` / `00009` はヒットし、`eeting` / `otes` はヒットしない。
日本語は連続する非 ASCII ランの先頭一致だけ(Ruling 17)。**上の「検索」節に実測表がある。**

### 3. `indexed: false` のバケットが Phase 0 と完全に同じ挙動をする ✅

**確認方法:** 同じ 4 キー(`cmp/a.txt` / `cmp/docs/b.md` / `cmp/docs/nested/c.md` / `cmp/z.bin`)を
`photos`(索引経路)と `media`(R2 経路)の両方にアップロードし、
`GET /objects?prefix=cmp/` と `?prefix=cmp/docs/` の JSON を突き合わせた。

**`bucketId` と `uploadedAt`(アップロード時刻が違う)を除いて完全一致した。**
`folders` / `objects` / `next` のすべてが同じ。
`media` の 1,100 件で `next.cursor` が R2 の opaque token のまま返り、
2 ページ目(100 件、`next: end`)も従来どおり取れることも確認した。

回帰テストとしては、`packages/api/test/objects.integration.test.ts`(R2 binding に直接 put して
一覧に出ることを見るファイル)の対象を `media` に移した。**`media` を `indexed: true` にするときは
このファイルを組み替えること。**

### 4. 索引を意図的に壊した状態でも `indexed: false` なら一覧が出る ✅

**確認方法:** dev を止めて `apps/web/.wrangler/state/v3/do`(索引 DO の SQLite が丸ごと入っている)を
削除し、`photos` が `indexed: false` の状態で起動して一覧を叩いた。

**`GET /objects?prefix=perf/` は 1,000 件を返した**(先頭 `perf/00000-a.jpg`、`next: more`)。
同じ状態で `GET /search?q=meeting` は 0 件を返した(索引が空なので正しい)。
**索引が完全に消えていても R2 経路の一覧は無傷である。**

### 5. `upsert` / `remove` の後に `search` の結果が追随する ✅

**確認方法:** Task 6 のテストで固定済み(`packages/api/src/object-index/object-index.test.ts`)。
今回の実測でも副次的に確認できている: seed した 10,000 件はすべてアップロード API 経由で
索引に入り、`q=meeting` / `q=notes` などで引ける。

テストが張っているのは次の 4 つ:

- `upsert` した key は FTS からも引ける
- 同じ key を 2 回 `upsert` しても FTS の行は増えない
- **`upsert` で name を変えると古い名前では引けず、新しい名前で引ける**(更新漏れの検出)
- `remove` した key は FTS からも消える

拒否された `upsert`(バケット guard)が `objects` / `prefixes` / `objects_fts` の
**どれにも 1 行も書かない**ことも別テストで張られている。

### 6. バックフィルを途中で止めて再実行すると、続きから進んで全件揃う ✅(**「続きから」の意味に注記**)

**確認方法:** `packages/api/test/backfill-pagination.integration.test.ts` が 1,001 件(= 2 ページ)を
置いてページ境界をまたがせ、`backfill_pages = 2` と全 1,001 件の取り込みを張っている。
今回の実測でも 10,000 件を `backfill_pages = 10` で取り切り、`status` が
`{"kind":"complete","indexed":10000}` になった。

**注記: 「続きから進む」が成り立つのは、alarm と alarm の間で中断した場合である。**
カーソルは `meta.backfill_cursor` に永続化されるので、DO が退避しても次の alarm が続きから進む
(**カーソルの保存を消すと 1 ページ目を舐め直して永久に終わらない**ことを上記テストが検出する)。

**`POST /index/backfill` を明示的に叩き直した場合は、設計上カーソルを先頭に戻して最初からやり直す**
(`startBackfill` の `#metaClear(BACKFILL_CURSOR_KEY)`)。「取りこぼしを作らない」側に倒した
意図的な判断であり、`upsert` が冪等なので**最終状態は同じく全件揃う。**
実測でも 2 回目の実行後に件数は増えず `complete` のままだった。

### 7. `ObjectDescriptor` と `NextPage` のワイヤ型が変わっていない ✅

**確認方法:** `git diff main -- packages/core` が空であることを確認した。

Ruling 18 の cursor タグは `NextPage.cursor`(クライアントから見て opaque な `string`)の
**中身**を変えただけで、**型は変えていない。**`apps/web` 側は `getNextPageParam` で
`last.next.cursor` をそのまま次のリクエストに載せるだけなので、変更は不要だった。

## この数字が言っていないこと

- **ローカル miniflare 上の数字である。**本番の Durable Object でも同じ比になる保証は無い。
  ローカルでは R2 も DO も同じプロセス・同じディスクの SQLite なので、
  **「R2 がネットワーク越しになる」という本番の最大の差が計測に入っていない**
- **本番の DO の起動コスト(cold start)を測っていない。**すべてウォームアップ済みの状態の数字である。
  索引経路は毎回 DO を経由するので、**本番では DO が寝ていた場合の初回だけ遅くなるはずだが、測っていない**
- **1 ユーザーの逐次アクセスしか測っていない。**同時アクセス下で DO が単一スレッドであることの
  影響(バックフィル中のブロックで片鱗が見えている)は測っていない
- **ブラウザの描画は測っていない。**Phase 0 の受け入れ基準 1(スクロールでフレーム落ちしない)は
  Task 16 レポートの領分であり、**索引を入れても直らない**とそこで結論が出ている
  (原因はページ追加のたびのコレクション再構築)
- **10,000 件という 1 つの規模でしか測っていない。**100 件 / 100,000 件でどうなるかは外挿でしかない。
  特にバックフィルは件数に線形なので、**100,000 件では 50 秒級になると予想されるが実測していない**
- **`media` は `indexed: false` のまま残してある。**本番相当の切り替えを 2 バケットで
  同時に踏んだわけではない
- **アップロード経路の索引書き込みコストを同一条件で before/after 測定していない。**
  seed が 27 秒 → 73.4 秒になっているが、マシンの状態も R2 の総量も違うので比較できない

## 切り替えの手順(次のバケットのために)

1. `POST /api/buckets/:id/index/backfill` を叩く(202 が返る)
2. `GET /api/buckets/:id/index/status` が `{"kind":"complete","indexed":N}` になるまで待つ。
   **`N` が R2 の実件数と一致することを確認する**
3. `packages/api/src/r2/registry.ts` の当該バケットの `indexed` を `true` にして再デプロイ

**この順を守ること。**`indexed: true` にしてからバックフィルを叩くと、バックフィル中の
一覧要求がその DO のブロックに巻き込まれる(上の「バックフィル」節の実測)。
また、**運用中に `indexed` を実行時に切り替えられるようにしてはいけない**
(`buckets/index.ts` の backfill エンドポイントのコメントに理由がある)。
