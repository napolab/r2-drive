# Task 16 — Phase 0 受け入れ確認(性能計測)

`docs/tasks.md` の Task 16 のうち、**ローカルで閉じる計測**を実施した記録である。
実 R2 への 5 GB 転送と実 Cloudflare Access 越しの検証は、外部状態と課金を伴うため本書の対象外。

計測日: 2026-08-17
対象コミット: `feat/task-16-perf-measurement`(`65b8153` から分岐)

## 結論

**受け入れ基準 1「10,000 オブジェクトのフォルダをスクロールしてもフレーム落ちしない」は未達である。**
計測 → 原因の切り分け → 2 つ修正 → 再計測、まで本書で行った。それでも未達である。

|              | 判定 | 根拠                                                                                             |
| ------------ | ---- | ------------------------------------------------------------------------------------------------ |
| 描画・仮想化 | ✅   | 10,000 件を積んだ状態でスクロールしても 50ms 超のフレームは 0 本。DOM 上のタイルは常時 16〜30 枚 |
| 実アプリ経路 | ❌   | 修正後も 3 秒あたりのフレーム数が 308 → 197 へ単調に劣化(103fps → 66fps 相当)                    |

**ボトルネックは仮想化ではない。**1 ページ追加するたびにコレクション全体が作り直されており、
**1 回の追加コストはページの件数ではなく、その時点のコレクション全体の件数で決まる。**
(ページを 10 倍にしても max が 249ms → 216ms としか変わらなかったことが根拠。詳細は「修正と再計測」)

したがって**ページサイズでは解けず、Phase 1 の D1 索引でも直らない。**
索引で速くなるのは list の応答であって、クライアント側の再構築ではない。

副次的に判明したこと(**1 と 3 は本書の中で修正済み。「修正と再計測」を参照**):

1. ~~**`PAGE_SIZE = 200` は効いていない。**~~ `include: ['httpMetadata']` のせいで R2 が 100 件に丸めており、
   10,000 件に 100 往復していた。**→ `include` を外して 1,000 件/ページにした。往復 110 → 19 回**
2. **画像プレビューは 15 秒のスクロールで 196 MB 転送する。**142px 四方の表示に 1280x960 を配っている(約 61 倍)。
   **初回訪問のこのコストは残っている**(派生サムネイルが要る)
3. ~~**`content` エンドポイントに `Cache-Control` が無い。**~~ 一度見た領域に戻るだけで全部再ダウンロードしていた。
   **→ content-addressed URL + `immutable` にした。再訪時の転送量 206 MB → 0 バイト**
4. 画像はフレーム時間には影響していない(`loading="lazy"` + `decoding="async"` が効いている)。**帯域だけの問題である**

### 修正後の到達点

| 指標               | 修正前                  | 修正後         | 基準          |
| ------------------ | ----------------------- | -------------- | ------------- |
| p95 フレーム時間   | 40.9 ms                 | **17.5 ms**    | ✅ 60fps 内   |
| long frame (>50ms) | 41 / 15 秒              | **13 / 18 秒** | ❌ 0 ではない |
| 件数による劣化     | 265 → 160 フレーム/3 秒 | **308 → 197**  | ❌ 残っている |
| 再訪時の転送量     | 206 MB                  | **0 バイト**   | ✅            |

**受け入れ基準 1 はまだ未達である。**通常のフレームは 60fps に収まるようになったが、
件数に比例した劣化と 200ms 級の long frame が残る。

再計測で機序がより正確になった: **1 回の追加コストはページの件数ではなく、その時点の
コレクション全体の件数で決まる**(ページを 10 倍にしても max が下がらなかったことが根拠)。
残る打ち手は「追加のたびにコレクション全体を作り直さない」ことであり、
**Phase 1 の D1 索引では直らない。**

## 何を、なぜ 3 層に分けたか

受け入れ基準 1 は「10,000 オブジェクトのフォルダをスクロールしてもフレーム落ちしない」である。
これを 1 回の計測で出すと、**遅かったときに原因が切り分けられない。**一覧は grid タイルに
実画像プレビューを出すため、「仮想化の描画コスト」と「画像の取得・デコード」と
「ページングのたびのコレクション再構築」が同じ数字に混ざるからである。

| 層                 | 測るもの                                  | 混ぜないもの                   |
| ------------------ | ----------------------------------------- | ------------------------------ |
| **A** 描画の床     | react-aria `Virtualizer` + タイル描画だけ | ネットワーク・ページング・画像 |
| **B** 実アプリ経路 | ページング + Query cache 込みの実挙動     | —                              |
| **C** 画像帯域     | プレビューの転送量とデコード              | —                              |

A は CI に残る回帰ゲート、B と C は一度きりの実測である。

## Layer A — 描画の床

### 方法

`apps/web/src/routes/-components/object-list/object-list.perf.browser.test.tsx`
(`pnpm test:browser` の管理下、playwright + chromium headless、viewport 800x700)

- 10,000 件の合成 `ObjectDescriptor` を `ObjectList` に直接流し込む
- **全件を `application/octet-stream` + `.bin` にする。**`resolveFileType` が `opaque` プラグインに
  落ち、プレビューが inline SVG のアイコンだけになる。モックを 1 行も書かずにネットワークが 0 になる
- ファイル名は長短 4 パターンを混ぜ、`lineClamp: 2` の折り返しコストを再現する
- ウォームアップで 1 周させ、そのサンプルは捨てる(アイドルからの 1 発目は必ず長く出るため)
- 判定は純粋関数 `judgeFrames`(`frame-budget/index.ts`)に分離。閾値は `LONG_FRAME_MS = 50`、
  許容本数は `LONG_FRAME_BUDGET`

### 計測条件を 2 つに分けた理由

総スクロール距離が 629,314px あるため、「1 パスを 3 秒に収める」と 1 フレームあたり 3,497px、
つまり **viewport の約 5 倍を飛ぶテレポート**になる。毎フレーム可視タイル 16 枚が全入れ替わる
最悪条件であり、人間がトラックパッドで弾いたときの挙動ではない。両方測る。

| パス         | ステップ幅                  | 打ち切り                 | 開始位置             |
| ------------ | --------------------------- | ------------------------ | -------------------- |
| `teleport`   | 3,497px(viewport の約 5 倍) | 末尾到達 or 180 フレーム | 先頭                 |
| `continuous` | 233px(viewport の 1/3)      | 180 フレーム             | `scrollHeight * 0.4` |

`continuous` を中ほどから始めるのは、先頭付近がウォームアップで温まっており条件が甘くなるため。

### 結果(3 回連続実行)

| run | パス       | sampleCount | longFrames | p50   | p95   | max   |
| --- | ---------- | ----------- | ---------- | ----- | ----- | ----- |
| 1   | teleport   | 180         | **0**      | 16.70 | 25.00 | 33.40 |
| 1   | continuous | 180         | **0**      | 8.30  | 8.50  | 9.80  |
| 2   | teleport   | 180         | **0**      | 16.70 | 25.00 | 32.50 |
| 2   | continuous | 180         | **0**      | 8.30  | 8.40  | 9.30  |
| 3   | teleport   | 180         | **0**      | 16.70 | 25.00 | 33.30 |
| 3   | continuous | 180         | **0**      | 8.30  | 9.10  | 9.40  |

(単位 ms)

補助的な数字:

| 項目                                  | 値                          |
| ------------------------------------- | --------------------------- |
| マウント(10,000 件の Collection 構築) | 174.2 〜 178.6 ms           |
| DOM 上に存在するタイル数              | **常時 16 枚**(10,000 件中) |
| `scrollHeight`                        | 630,012 px                  |

### 読み方

- **`visibleTiles = 16` が仮想化が効いていることの実証である。**素の DOM 展開なら 10,000 枚が
  居座り、スクロール以前にマウントで死ぬ
- `teleport` の `p50 = 16.70ms` は 60Hz の 1 周期にちょうど一致する。タイル全入れ替えの仕事量が
  1 vsync 周期に収まっている、と読むのが妥当
- **`continuous` の `p50 = 8.30ms` を「120fps 出ている」と読んではならない。**headless Chromium の
  rAF は実ディスプレイの vsync とロックされていないため、フレームの仕事が軽ければコールバックが
  そのぶん早く回るだけである。teleport の約半分という**相対値**が「タイルが大半再利用されて
  1 フレームの仕事が軽い」ことの証拠になる、という読み方までが正しい
- マウント 174〜179ms は記録のみで合否に使わない。実アプリは 1 ページずつ積み上がるので、
  10,000 件を一度に構築する条件は発生しない
- **ここで「積み上がる過程は測っていない」ことが、後の Layer B で効いてくる。**
  Layer A が測っているのは「積み終わった後」だけである

### 判定

**受け入れ基準 1 は Layer A の範囲で満たしている。**6 verdict すべてで 50ms 超のフレームは 0 本。
閾値に対するマージンは teleport で約 1.5 倍、continuous で約 5 倍。

`LONG_FRAME_BUDGET = 0`(ノイズを一切許容しない)を採用した。**マージンが薄いのは teleport 側**
なので、将来 CI が flaky になるならそこから出る。そのときは budget を上げる前に、
まず「本当に遅くなったのか」を疑うこと。

### この数字が言っていないこと

- **実ディスプレイでの体感ではない。**headless の rAF は vsync と切り離されている。絶対値ではなく
  同条件での相対値として扱う。体感の裏取りは Layer B の実 trace が担う
- ネットワーク・ページング・画像デコードを一切含まない。**「描画は白い」までしか言っていない**

## Layer B — 実アプリ経路

### 方法

- `pnpm --filter web dev`(vite + `@cloudflare/vite-plugin` = workerd + ローカル R2)
- `apps/web/scripts/seed-r2.ts` で **10,000 オブジェクトを `perf/` 配下に投入**
  (26.8 秒 / 373 obj/s)。内訳は `.bin` 7,000 件(256〜640B)と
  **本物の baseline JPEG 3,000 件**(1280x960 グレースケール、125,132 B)。画像は 10 件ごとに 3 件の割合で散らす
- 実 Chrome(headless ではない)を Chrome DevTools 経由で駆動。viewport 1280x900
- `requestAnimationFrame` の中で `scrollTop` を `clientHeight / 3`(261px)ずつ加算する連続スクロール

**Layer A と違い、これは headless ではない実ブラウザである。**フレーム時間は vsync に紐づいている。

### 結果 1: 初回スクロール(ページングが走る)

| 項目                   | 値                         |
| ---------------------- | -------------------------- |
| サンプル               | 1,085 フレーム / 15 秒     |
| **long frame (>50ms)** | **41 本**                  |
| p50 / p95 / max        | 8.4 / 40.9 / **249.3** ms  |
| list API リクエスト    | **110 回**                 |
| DOM 上のタイル / img   | 30 枚 / 9 枚(最後まで一定) |

**Layer A では 0 本だった long frame が、実アプリでは 41 本出る。**
仮想化は最後まで崩れていない(タイル 30 枚のまま)ので、原因は描画ではない。

### 結果 2: 劣化はコレクション件数に単調に比例する

同じスクロールを 3 秒ごとに区切って集計した。

| 経過   | 読込済み件数(概算) | 3 秒あたりのフレーム数 | long frame | p95       | max   |
| ------ | ------------------ | ---------------------- | ---------- | --------- | ----- |
| 0–3s   | 1,374              | 265(≈88fps)            | 5          | 24.9      | 91.7  |
| 3–6s   | 2,547              | 246                    | 8          | 41.8      | 117.5 |
| 6–9s   | 3,620              | 206                    | 14         | 66.6      | 98.1  |
| 9–12s  | 4,600              | 203                    | 10         | 42.0      | 166.2 |
| 12–15s | 5,480              | 180                    | 12         | 66.7      | 145.9 |
| 15–18s | 6,359              | **160(≈53fps)**        | 12         | **116.4** | 173.8 |

(時間は ms)

**フレームレートが 88fps から 53fps へ単調に落ちている。**スクロール速度も同時に落ちる
(1 フレームが長くなるため、同じ 3 秒で進める距離が減る)。

### 結果 3: 切り分け — ページングを止めると消える

同じ領域を、既にコレクションに載った状態で往復させた(= ページングが発生しない)。

| 条件                                         | long frame | p95  | max   | 画像リクエスト |
| -------------------------------------------- | ---------- | ---- | ----- | -------------- |
| 初回(ページングあり)                         | **41**     | 40.9 | 249.3 | 1,641          |
| 逆方向(ページングなし)                       | **1**      | 17.3 | 99.7  | 1,647          |
| 順方向・2 回目(ページングなし)               | **6**      | 16.8 | 149.8 | 1,290          |
| 画像を `display:none` で消す(ページングなし) | **3**      | 16.7 | 149.0 | 0              |

**スクロールも描画も画像も同じままで、ページングの有無だけが 41 と 1〜6 を分けている。**
画像を完全に消しても long frame は減らない(6 → 3)ので、**画像はフレーム時間の原因ではない**
(`loading="lazy"` + `decoding="async"` が効いている)。

### 判定

**受け入れ基準 1 は実アプリ経路では満たしていない。**

Layer A(10,000 件を最初から積んだコレクションをスクロールする)は白い。
つまりボトルネックは**描画でも仮想化でもなく、1 ページ追加するたびに走るコレクション再構築**である。
件数に比例して 1 回の追加コストが上がるため、積み上がるほど遅くなる。

**この機序は仮説ではなく、上の 3 つの結果が支えている**(件数との単調な相関 + ページング除去で消える +
画像除去では消えない)。ただし「react-aria のコレクション再構築が O(n)」であること自体は
プロファイラのコールツリーまで降りて確認していない。**そこは未確認である。**

### 副産物: `PAGE_SIZE = 200` は効いていない

`packages/api/src/r2/list.ts:8` は `PAGE_SIZE = 200` だが、**実測は 1 ページ 100 件**
(10,000 件に対して list API が 110 回)。

原因は同ファイル 23 行目の `include: ['httpMetadata']` である。Cloudflare の公式ドキュメントに
明記されている:

> When requesting metadata like `httpMetadata` or `customMetadata`, the total amount of data
> returned in a single operation is limited, which may result in fewer objects being returned
> than the specified limit. Applications should rely on the `truncated` property rather than
> the object count.

**ページングのロジック自体は正しい。**`list.ts:43` は `listed.truncated` を見ており、
ドキュメントが警告している「件数で判定するアンチパターン」は踏んでいない。

壊れているのは**周辺の記述**である。

| 場所                                                       | 記述                                      | 実態           |
| ---------------------------------------------------------- | ----------------------------------------- | -------------- |
| `apps/web/src/routes/-components/object-list/index.tsx:32` | 「1 ページ 200 件」                       | 100 件         |
| `docs/tasks.md`                                            | 「201 個入れないと truncated にできない」 | 101 個で足りる |
| `packages/api/src/r2/list.ts:8`                            | `PAGE_SIZE = 200`                         | 実効 100       |

**10,000 件に到達するのに 50 往復ではなく 100 往復している。**結果 2 の劣化はページ数に比例するので、
これは直接コストである。

## Layer C — 画像プレビューの帯域コスト

### 結果

15 秒の連続スクロール 1 回で:

| 項目                 | 値                            |
| -------------------- | ----------------------------- |
| 画像リクエスト       | **1,641 件**                  |
| 転送量               | **205,833,912 B = 196 MB**    |
| `decodedBodySize`    | 205,341,612 B(≒ 転送量)       |
| 1 ビューポートあたり | img 9 枚 x 122KB ≈ **1.1 MB** |

`decodedBodySize` が転送量とほぼ同じなので、**gzip / brotli の余地は無い**(JPEG は既に圧縮済み)。
**帯域を減らす手段は「小さい画像を配る」しかない。**

### 何が無駄になっているか

|                        | 値                        |
| ---------------------- | ------------------------- |
| 配信している画像       | 1280 x 960 = 1,228,800 px |
| 実際に描画されるサイズ | 142 x 141 = 20,022 px     |
| 比                     | **約 61 倍**              |

一覧のタイルは 142px 四方である。そこに 1280x960 を落としている。

### さらに: キャッシュが効いていない

`GET /api/buckets/:bucketId/content/:key` のレスポンスヘッダを実測した。

```
status: 200
etag: "e6424dda1e57daba7025844e70b25d4c"
cache-control: (無し)
expires: (無し)
```

**`Cache-Control` が付いていない。**結果として、一度見た領域へスクロールで戻るだけで
**同じ画像を全部再ダウンロードする**(逆方向スクロールで 1,647 リクエスト / 206 MB を実測。
304 ではなく本体 125,132 B が毎回流れている)。

つまり帯域コストは「10,000 件を 1 回舐めて 196 MB」ではなく、**スクロールして通過するたびに毎回 196 MB** である。

### Phase 1 への含意

**派生サムネイルの優先度は高い。**ただし打ち手は 2 つあり、コストが全く違う。

1. **`Cache-Control` を付ける**(即日・数行)。R2 オブジェクトは etag で不変性が判定できるので
   `immutable` に近い扱いができる。**再訪時の帯域がゼロになる**。派生サムネイルより先にやるべき
2. **派生サムネイルを持つ**(Phase 1 の `ObjectHook` の実装 1 つ)。初回訪問の 196 MB を
   1/60 程度に落とす。142px 表示なら 2x で 284px あれば足りる

1 は Phase 1 を待つ必要が無い。2 の前に済ませておくと、2 の効果測定が綺麗に取れる。

## 修正と再計測

計測を受けて 2 つ直し、**同じ手順・同じ seed データで測り直した。**

### 修正 1: 1 ページ 100 件 → 1,000 件

`include: ['httpMetadata']` を外し、`limit` を `ListInput` の必須フィールドにした
(`packages/api/src/r2/list.ts` / `plugins/object-source/r2-list/index.ts`)。

代償として `contentType` は保存済み `httpMetadata` ではなく**拡張子から決まる**。
単体取得(`content` エンドポイント)は `get()` の値をそのまま返すので影響しない。

`limit` を注入できるようになったので、`docs/tasks.md` にあった
「`PAGE_SIZE` がモジュール定数なので 201 個入れないと truncated にできない」という
テストの穴も同時に閉じた(3 件 + `limit: 2` でカーソル往復を固定)。

### 修正 2: content-addressed URL + `Cache-Control`

preview / download / upload 完了の URL に `?v=<etag>` を載せ、`v` がオブジェクトの etag と
一致するときだけ `private, max-age=31536000, immutable` を返す。一致しない / 無いときは
`private, no-cache`(`packages/api/src/buckets/index.ts`)。

**`hono/cache` は使わなかった。**エッジキャッシュはクライアントへの転送量を減らさないので、
計測した問題(ブラウザの再ダウンロード 196 MB)を解かない。加えて既定では 206 が
キャッシュ対象外であり、Access 配下の非公開ファイルをゾーン共有キャッシュに置く判断も要る。
**R2 の Class B オペレーション削減が目的になった時点で再検討する。**

### 結果: 初回スクロール(18 秒)

| 指標                                | 修正前    | 修正後        |
| ----------------------------------- | --------- | ------------- |
| list API リクエスト                 | 110       | **19**        |
| long frame (>50ms)                  | 41(15 秒) | **13**(18 秒) |
| p95                                 | 40.9 ms   | **17.5 ms**   |
| max                                 | 249.3 ms  | 216.3 ms      |
| 3 秒あたりのフレーム数(最初 → 最後) | 265 → 160 | **308 → 197** |

| 経過   | frames | long frame | p95  | max   |
| ------ | ------ | ---------- | ---- | ----- |
| 0–3s   | 308    | 1          | 16.7 | 58.1  |
| 3–6s   | 295    | 2          | 16.6 | 216.3 |
| 6–9s   | 259    | 1          | 17.4 | 166.7 |
| 9–12s  | 241    | 3          | 17.5 | 166.4 |
| 12–15s | 223    | 2          | 17.5 | 200.0 |
| 15–18s | 197    | 4          | 25.2 | 208.3 |

### 結果: 再訪(既に見た領域へ戻る)

| 指標           | 修正前     | 修正後                               |
| -------------- | ---------- | ------------------------------------ |
| 画像リクエスト | 1,647      | 1,351                                |
| **転送量**     | **206 MB** | **0 バイト**(全件ブラウザキャッシュ) |

`transferSize` が全 1,351 件で 0。`decodedBodySize` は 169 MB あるので、
**中身は表示されていて、ネットワークだけが消えている。**

### 読み方: max が下がらなかったことが機序を確定させた

事前に「1 ページを 10 倍にすると 1 回の追加が 10 倍重くなり、max が悪化するのでは」という
懸念を挙げていた。**実際には max はほぼ変わらなかった**(249.3 → 216.3)。

つまり **1 回の追加コストはページの件数ではなく、その時点のコレクション全体の件数で決まる。**
O(ページサイズ) ではなく O(総件数) である。だから:

- ページを 10 倍にすると**高価な追加の回数が 1/10 になる**(長いフレームの本数が減る)
- **1 回あたりの長さは変わらない**(max が下がらない)

これは「ページングが原因」という当初の結論を、より正確な形に置き換える。
**原因はページングそのものではなく、追加のたびにコレクション全体を作り直していること**である。

### 判定: 改善したが、受け入れ基準 1 はまだ未達

- p95 が 40.9 → 17.5ms になり、**通常のフレームは 60fps に収まっている**
- しかし **3 秒あたりのフレーム数は依然 308 → 197 へ単調に落ちる**(103fps → 66fps 相当)。
  件数に比例する劣化は残っている
- **200ms 級の long frame も残る**(18 秒で 13 本)

残る打ち手は「追加時にコレクション全体を作り直さない」方向であり、ページサイズでは解けない。
react-aria のコレクション実装かデータ構造の側の問題なので、**Phase 1 で D1 索引を入れても直らない。**
着手前に react-aria 側の挙動をプロファイラのコールツリーで確認すること。

## 付随して観測されたもの: CLS は約 100 だが、追う意味は無い

DevTools の trace が CLS 7.03 を報告し、自前の `PerformanceObserver` でも
1 パスあたり layout shift の総和 85〜115(イベント 800〜1,000 件)を観測した。「良い」とされる 0.1 の
1000 倍である。

**しかしこれは UI の欠陥ではない。**切り分けの結果:

| 条件                           | layout shift 総和 |
| ------------------------------ | ----------------- |
| ページングあり・画像あり       | 84.9              |
| ページングなし・画像あり       | 93.5 / 108.7      |
| ページングなし・**画像を消す** | **114.6**         |

**画像を消しても減らない。ページングを止めても減らない。**残る原因は
react-aria の `Virtualizer` が可視行を `top` / `left` の再代入で配置し直していることである。
仕様上これは「要素が動いた」= layout shift として計上されるが、**仮想化の動作そのもの**であり、
利用者から見て何かがガタつくわけではない。

**この UI で CLS を指標として使わないこと。**数字を下げようとすると仮想化を捨てることになる。
(`transform` ベースの配置なら合成レイヤ扱いで計上されないが、それは react-aria 側の実装であり
本リポジトリで変えるものではない)

## アップロード中断時の abort について

Task 16 の最終項目として明記する。

**タブを閉じたときの multipart abort は best-effort である。**ブラウザは `visibilitychange` /
`pagehide` 中に開始された非同期 API の完了を保証しない。`fetch(..., { keepalive: true })` や
`sendBeacon` を使っても「送信を試みる」までであり、**サーバー側で `abortMultipartUpload` が
実行されたことは保証されない。**

したがって、次の 2 点を偽装しないこと。

1. UI で「中断しました」と表示することは、サーバー側のゴミが消えたことを意味しない
2. 完了保証が要るなら、**中断検出をサーバー側に置く**しかない(未完了 multipart の TTL 掃除)。
   これは `uploadId` の永続化を伴い、Phase 0 のスコープ外である
   (spec §13 の「4 の『中断からの再開』は含まない」と同じ理由)

明示的に abort ボタンを押した経路、およびアップロード失敗時の経路については、
Phase 0 で `abortMultipartUpload` を呼ぶところまでを責任範囲としている。
